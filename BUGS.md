# Known Bugs & Limitations

Updated after every work session. See [CLAUDE.md](CLAUDE.md) (not committed) for the full technical rationale behind these; this file is the committed, user-facing summary.

## Fixed during initial development (kept here for history/context)

- **Timestamp comparison bug (fixed)**: session timestamps were originally stored with `DateTime.ToString("O")`, which formats differently depending on `DateTimeKind`. This caused `GetSessionsForYear` to sometimes silently exclude sessions near a year boundary, and caused imported/recorded times to be off by exactly the local UTC offset on read-back. Fixed by switching to a fixed custom timestamp format and removing a spurious `ToLocalTime()` call. Caught by `SessionTrackerTests` and `RecapAggregatorTests` before release.
- **SQLite provider swapped from Microsoft.Data.Sqlite to System.Data.SQLite (fixed, real install failure)**: the plugin was installed into a live Playnite instance and genuinely failed to load — confirmed in Playnite's own `playnite.log`. `Microsoft.Data.Sqlite` pulls in a `netstandard2.0`-oriented dependency chain (`SQLitePCLRaw.core`, `System.Memory`, `System.Buffers`, `System.Runtime.CompilerServices.Unsafe`, `System.Numerics.Vectors`) at exact assembly versions that collided with the older versions Playnite's own .NET Framework process already has loaded — and a plugin has no way to add its own binding-redirect policy to the host process. First attempt (pinning `SQLitePCLRaw.bundle_e_sqlite3` to exactly match) fixed the unit-test host but Playnite itself still failed with `FileNotFoundException` for `SQLitePCLRaw.core`. Fixed properly by switching to `System.Data.SQLite.Core`, a single self-contained ADO.NET provider with no such shim chain — confirmed via `playnite.log` that Astra now loads cleanly (`Loaded plugin: Astra, version 0.1.0`, no errors).
- **Newtonsoft.Json version pinned to 10.0.3 (fixed, same root cause as above)**: for the same reason, referencing the latest Newtonsoft.Json (13.x, assembly version 13.0.0.0) would load a second, conflicting Newtonsoft.Json identity next to Playnite's own already-loaded copy (assembly version 10.0.0.0). Verified by extracting several `.nupkg`s directly that NuGet package versions 10.0.1–10.0.3 are the ones whose DLL carries assembly version 10.0.0.0, matching Playnite's exactly. **Trade-off, not silently accepted**: this pins Astra to a Newtonsoft.Json release with a known advisory (GHSA-5crp-9r3c-p9vr, a stack-overflow-via-deeply-nested-JSON denial-of-service, fixed upstream only at 13.0.1+, which is not assembly-version-compatible with Playnite's host process). Real-world exposure here is low: Astra only ever deserializes JSON it wrote itself (recap export) or GameActivity's own local session files on the same machine — never network input — but it's the same vulnerable version Playnite itself already ships, so this isn't a regression Astra introduces on its own.
- **"Edit playtime..."/"Reset to tracked value" did nothing when clicked (fixed, real user-reported bug)**: the right-click `ContextMenu` was bound with `Command="{Binding DataContext.EditPlaytimeCommand, RelativeSource={RelativeSource AncestorType=ListBox}}"`. A WPF `ContextMenu` renders in its own popup, not the visual tree of the row it's attached to, so `RelativeSource AncestorType=ListBox` from inside it finds nothing — the `Command` silently bound to `null` and clicking the menu item was a no-op, with no error anywhere. Fixed using the standard `PlacementTarget` workaround: the row's `DockPanel` carries the view model via its `Tag`, and the menu items bind through `PlacementTarget.Tag`/`PlacementTarget.DataContext` (searching `AncestorType=ContextMenu`, which works because the `MenuItem` actually is inside the `ContextMenu`'s own tree). Confirmed the plugin still loads cleanly after the fix; the click-through behavior itself still needs a manual check since no UI-automation tool is available in this session (see TESTING.md §9).
- **Most Played showed no rows at all despite real tracked data (fixed, real user-reported bug, two separate causes)**:
  1. The list-view redesign gave each row's "⋮" button its own `ContextMenu="{Binding ElementName=RowRoot, Path=ContextMenu}"`, pointing at the *same* `ContextMenu` instance the row's own `Grid.ContextMenu` already owned. A `ContextMenu` (like any `FrameworkElement`) can only have one logical owner at a time; assigning the same instance to a second element throws `InvalidOperationException` ("already the logical child of another element") the moment that row's template is applied — which happens for every row, so every row silently failed to render and the whole list looked empty even though `MostPlayedViewModel.Entries` was correctly populated (confirmed by the fact that Home's identically-sourced "Top Played" row displayed fine). Fixed by never assigning the `ContextMenu` to a second owner: the button now carries a plain `Tag="{Binding ElementName=RowRoot}"` reference instead, and its `Click` handler opens `row.ContextMenu.IsOpen = true` directly on the row's own `Grid` — same menu, same `PlacementTarget`, no dual ownership.
  2. After fixing (1), the list was **still** empty. Second cause: the rank number's `Foreground` used `TargetNullValue="{DynamicResource TextBrush}"` to recover when `RankToColorConverter` returned `null` for rank > 3. Nesting a `{DynamicResource}` markup extension inside a `Binding`'s `TargetNullValue` is invalid — `DynamicResource`/`Binding` can only target an actual `DependencyProperty` on a `DependencyObject` directly, not a nested CLR sub-property like `TargetNullValue` — and this throws when the row's shared `DataTemplate` is first loaded, which (same as cause 1) kills rendering for every row at once, plus adds real per-exception overhead that likely explains the reported "Most Played sometimes doesn't respond or takes a long time to open." Fixed by having the converter return `DependencyProperty.UnsetValue` instead of `null` for rank > 3 (which correctly leaves `Foreground` unset, falling through to the inherited `DynamicResource`-bound value from `UserControl.Foreground`) and removing `TargetNullValue` entirely.
  
  **General lesson for any future Astra XAML**: `{DynamicResource}` and `{Binding}` must be applied directly to a `DependencyProperty` — never nested inside another markup extension's own sub-property (`TargetNullValue`, `FallbackValue`, `ConverterParameter`, etc.). A converter that wants to say "use whatever the property would otherwise be" should return `DependencyProperty.UnsetValue`, not `null`.

- **XAML root-element event attribute caused `CS0426: The type name 'Views' does not exist in the type 'Astra'` (fixed, real build failure hit while adding `TrendChartControl`)**: wiring `SizeChanged="OnSizeChanged"` as an XAML attribute directly on a `UserControl`'s root element makes the markup compiler generate a fully-qualified cast in `InitializeComponent`'s `Connect()` method, e.g. `((Astra.Views.TrendChartControl)(target)).SizeChanged += ...`. Because the plugin's own `GenericPlugin` subclass is literally named `Astra` inside namespace `Astra` (see `Astra.cs`), the C# compiler resolves the leading `Astra` identifier to that class - found in the immediately-enclosing namespace - before it considers the outer `Astra` *namespace*, so `Astra.Views.TrendChartControl` gets parsed as "look for a nested type `Views` inside class `Astra`," which doesn't exist. This is invisible for every other existing view (`HomeView`, `RecapView`, etc.) because none of them wire a root-element event via a XAML attribute - element-level event handlers (e.g. `MouseLeave` on an inner `Canvas`) don't hit this path, since their generated cast target type is a plain WPF type (`System.Windows.Controls.Canvas`), not `Astra.Views.*`. **Fixed by wiring the event in code-behind instead** (`SizeChanged += (s, e) => Redraw();` in the constructor) rather than as a XAML attribute. **General lesson for any future Astra `UserControl`**: never attach an event via a XAML attribute directly on the root element (`<UserControl ... SomeEvent="Handler">`) - always wire it in the constructor's code-behind, specifically because this project's root namespace collides with its own plugin class name.

## Known limitations (by design, not bugs)

- **Sessions interrupted by a crash are lost.** Astra records a session only when `OnGameStopped` fires (which is when Playnite reports `ElapsedSeconds`). If Playnite or the game crashes hard enough that `OnGameStopped` never fires, that play time is not recorded. This matches a fundamental limit of Playnite's event model, not something Astra can work around without its own polling/heartbeat (out of scope for v1).
- **Playnite doesn't track sessions natively** — only cumulative `Playtime`/`PlayCount`. Astra's own session log only covers time played *since Astra was installed*; historical playtime predating installation cannot be broken into individual sessions (only the GameActivity import path, where available, can backfill session-level history).
- **GameActivity import is best-effort.** The on-disk format (`ExtensionsData/<guid>/GameActivity/<gameId>.json`) is undocumented and was reverse-engineered from an installed v3.5 copy. A future GameActivity release could change this format silently; Astra reports files it couldn't parse (`FilesFailedToParse`) rather than crashing, but does not validate the *semantics* of a changed schema — malformed data resembling the old shape could import incorrectly. Import is always user-triggered, never automatic.
- **No net462 reference assemblies on this dev machine** — the project targets **net472** instead. Runtime-compatible with any Windows 10/11 install, but flagging as a deliberate deviation from the more common net462 target seen in other Playnite plugins.
- **Sidebar icon is a placeholder.** `icon.png` is a generated solid-color square, not a designed asset — cosmetic only.
- **Editing a game's yearly playtime only corrects the displayed/exported total — it does not rewrite or redistribute the underlying session rows.** The `Sessions` table is untouched by an edit; a `PlaytimeOverrides` row (keyed by GameId+Year) is applied on top of the computed sum whenever the recap is built. This means `SessionCount` and the year's `ActiveDays`/`TotalSessions` intentionally stay based on real tracked sessions even after an edit — only the hours number is corrected, so activity/streak stats don't silently become fictional just because a playtime number was fixed. A future feature that exports or displays individual sessions would need to separately decide whether to respect overrides.
- **A playtime override only applies to games that already have at least one tracked session in that year** — there's no UI path to set one for a game with zero sessions, so an override can't "invent" an entry in the recap for a game that was never played that year.
